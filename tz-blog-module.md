# ТЗ (дополнение): Модуль «Блог / Статьи»

**Статус:** дополнение к основному ТЗ проекта
**Версия:** 1.0

---

## 1. Цель

Добавить в проект раздел блога, который позволяет:

1. Контент-менеджеру **самостоятельно, без разработчика** создавать, редактировать, планировать и публиковать статьи через админку.
2. Читателю удобно потреблять контент (чистая типографика, оглавление, время чтения).
3. **Удерживать читателя в блоге:** после того как пользователь дочитал статью, ему показывается блок рекомендованных материалов — с ручным подбором редактором и автоматическим fallback.

---

## 2. Публичная часть

### 2.1. Страница списка статей — `/blog`

- Сетка карточек статей (desktop 3 колонки → tablet 2 → mobile 1).
- Карточка статьи: обложка (16:9), категория (бейдж), заголовок, лид (2–3 строки, обрезка `…`), дата публикации, время чтения («5 хв читання»), автор (аватар + имя) — опционально.
- **Featured-блок** сверху: 1 закреплённая статья крупной карточкой (флаг `isFeatured` в админке).
- Фильтр по категориям — горизонтальный ряд «таблеток», активная подсвечена. URL: `/blog?category=slug`.
- Пагинация: кнопка «Показати ще» (подгрузка) либо классическая нумерация — **выбрать одно, зафиксировать до старта вёрстки**.
- Пустое состояние: иллюстрация + «Тут поки що порожньо».
- Состояние загрузки: скелетоны карточек.

### 2.2. Страница статьи — `/blog/[slug]`

Структура сверху вниз:

1. **Хедер статьи:** хлебные крошки (`Головна → Блог → Категорія`), категория, H1, лид, метаданные (дата, время чтения, автор), обложка.
2. **Оглавление (ToC):** автогенерация из H2/H3. На desktop — sticky-сайдбар слева/справа с подсветкой активной секции при скролле. На mobile — сворачиваемый аккордеон под лидом.
3. **Тело статьи.** Поддерживаемые блоки (см. §4.2).
4. **Прогресс-бар чтения** — тонкая полоса вверху экрана, заполняется по мере скролла.
5. **Подвал статьи:** теги, кнопки шеринга (Telegram, Facebook, X, копировать ссылку), блок автора (аватар, имя, био, ссылки).
6. **🔑 Блок рекомендованных статей** — см. §3.
7. CTA-блок (подписка / скачать приложение / связаться) — конфигурируется глобально в админке.

## 3. 🔑 Блок рекомендаций «Читайте далі»

Ключевое требование. Разбито на логику подбора и логику показа.

### 3.1. Логика подбора статей

Приоритет источников — сверху вниз:

| Приоритет | Источник | Описание |
|---|---|---|
| 1 | **Ручной подбор** | Редактор в админке вручную выбирает до **3** статей через поиск-автокомплит. Порядок — drag & drop. |
| 2 | **Авто: те же теги** | Если вручную выбрано < 3, добор статей с максимальным пересечением тегов. |
| 3 | **Авто: та же категория** | Добор по категории, сортировка — сначала свежие. |
| 4 | **Авто: свежие** | Последний fallback — просто последние опубликованные. |

Правила:

- Всегда отдаётся **ровно 3 статьи** (или меньше, если в блоге < 4 статей — тогда блок скрывается при 0).
- Текущая статья **исключается** из выдачи всегда.
- Черновики, снятые с публикации и отложенные статьи в рекомендации **не попадают**.
- Дубли исключаются: статья, добавленная вручную, не приходит повторно из авто-добора.
- Расчёт выполняется на сервере при рендере страницы (не на клиенте).

### 3.2. Логика показа («когда юзер дочитал»)

- Блок физически находится в DOM сразу после подвала статьи, но:
- **Триггер «дочитал»** = пользователь доскроллил до конца тела статьи (последний абзац пересёк 60% высоты вьюпорта). Реализация — `IntersectionObserver` на сентинел-элементе после последнего блока контента.
- При срабатывании триггера блок **плавно появляется**: `opacity 0 → 1`, `translateY 24px → 0`, длительность 500 мс, `ease-out`, карточки со stagger 80 мс.
- Появление происходит **один раз за сессию просмотра статьи** (не повторяется при скролле вверх-вниз).
- Fallback: если JS отключён или `prefers-reduced-motion: reduce` — блок отрисован статически, без анимации, но виден.
- **Важно:** блок не «выпрыгивает» поверх контента и не сдвигает layout (никаких layout shift, CLS = 0) — место под него зарезервировано.

### 3.3. Вёрстка блока

- Заголовок секции: «Читайте далі» / «Схожі статті» (текст редактируется в админке).
- 3 карточки в ряд (desktop) → горизонтальный скролл со snap (mobile).
- Карточка: обложка, категория, заголовок (2 строки max), время чтения.
- Hover: лёгкий подъём карточки + масштаб обложки 1.04.

### 3.4. Аналитика блока

Отправлять события (GA4 / Meta Pixel / другое — уточнить):

| Событие | Когда | Параметры |
|---|---|---|
| `article_read_complete` | Сработал триггер «дочитал» | `article_id`, `slug`, `time_on_page` |
| `recommendations_view` | Блок появился во вьюпорте | `article_id`, `recommended_ids[]`, `source` (`manual`/`auto`) |
| `recommendation_click` | Клик по карточке | `from_article_id`, `to_article_id`, `position` (1–3), `source` |

Это даёт возможность мерять CTR блока и сравнивать ручной подбор с автоматическим.

## 4. Админка

### 4.1. Список статей

- Таблица: обложка (мини), заголовок, категория, статус, автор, дата публикации, просмотры.
- Статусы: `Чернетка` / `Заплановано` / `Опубліковано` / `Знято з публікації` — цветные бейджи.
- Фильтры: по статусу, категории, автору. Поиск по заголовку.
- Массовые действия: опубликовать, снять с публикации, удалить.
- Действия в строке: редактировать, дублировать, **предпросмотр**, удалить.

### 4.2. Редактор статьи

**Требование: WYSIWYG-редактор, без Markdown-синтаксиса для контент-менеджера.**

Поля:

| Поле | Тип | Обязательно |
|---|---|---|
| Заголовок (H1) | текст | да |
| Slug | текст, автогенерация из заголовка + ручная правка + проверка уникальности | да |
| Лид / краткое описание | textarea, 160–200 симв., счётчик | да |
| Обложка | загрузка изображения + alt-текст | да |
| Категория | select (одна) | да |
| Теги | multi-select с созданием на лету | нет |
| Автор | select из пользователей | да |
| Тело статьи | rich-text редактор | да |
| **Рекомендованные статьи** | до 3 шт., поиск-автокомплит по заголовку, drag & drop сортировка | нет |
| Статус | select | да |
| Дата публикации | datetime picker (можно в будущем → «Заплановано») | да |
| Featured | чекбокс | нет |
| SEO: meta title | текст (fallback = заголовок), счётчик до 60 симв. | нет |
| SEO: meta description | textarea (fallback = лид), до 160 симв. | нет |
| SEO: OG-изображение | загрузка (fallback = обложка) | нет |
| `noindex` | чекбокс | нет |

Блоки внутри тела статьи:

- Параграф, H2, H3
- Маркированный / нумерованный список
- Цитата (blockquote)
- Изображение (с подписью и alt)
- Галерея (2–4 изображения)
- Ссылка (внутренняя / внешняя, внешние — `target="_blank" rel="noopener"`)
- Разделитель
- Callout / врезка (info / warning / success)
- Embed: YouTube, Telegram-пост
- Таблица
- Блок кода (если тематика требует)

Функции редактора:

- **Автосохранение черновика** каждые 30 сек + индикатор «Збережено о 14:32».
- **Предпросмотр до публикации** — кнопка открывает статью на публичном шаблоне по секретной ссылке (`/blog/[slug]?preview=TOKEN`), доступной без авторизации, чтобы можно было отправить клиенту.
- Загрузка изображений drag & drop, автоматическая конвертация в WebP, ресайз до max 1600px по ширине, генерация `srcset`.
- Валидация перед публикацией: пустой slug, нет обложки, нет alt у изображений → предупреждение (не блокирующее, кроме slug).

### 4.3. Управление категориями и тегами

Отдельный раздел: CRUD категорий (название, slug, описание, цвет бейджа) и тегов. Запрет удаления категории, к которой привязаны статьи (сначала перенести).

### 4.4. Роли

| Роль | Права |
|---|---|
| Адміністратор | всё, включая пользователей и настройки |
| Редактор | создавать/редактировать/публиковать любые статьи, управлять категориями |
| Автор | создавать и редактировать **свои** статьи, отправлять на публикацию (без права публиковать) |

## 5. Модель данных

```ts
type Article = {
  id: string;
  slug: string;                 // уникальный
  title: string;
  excerpt: string;
  coverImage: { url: string; alt: string };
  body: ContentBlock[];         // структурированный JSON, не сырой HTML
  categoryId: string;
  tagIds: string[];
  authorId: string;

  // рекомендации
  relatedArticleIds: string[];  // до 3, ручной подбор, порядок значим

  status: 'draft' | 'scheduled' | 'published' | 'unpublished';
  publishedAt: string | null;   // ISO
  isFeatured: boolean;

  seo: {
    metaTitle?: string;
    metaDescription?: string;
    ogImage?: string;
    noindex: boolean;
  };

  readingTimeMinutes: number;   // вычисляется автоматически: слова / 200
  viewsCount: number;
  createdAt: string;
  updatedAt: string;
};

type Category = { id: string; slug: string; title: string; description?: string; color?: string };
type Tag      = { id: string; slug: string; title: string };
type Author   = { id: string; name: string; avatarUrl?: string; bio?: string; socials?: Record<string,string> };
```

## 6. SEO и техническое

- Каждая статья: `<title>`, `<meta description>`, canonical, Open Graph + Twitter Card.
- **JSON-LD `Article`** (headline, image, datePublished, dateModified, author, publisher) + `BreadcrumbList`.
- `sitemap.xml` — автоматически включает все опубликованные статьи и страницы категорий, обновляется при публикации.
- `/blog/rss.xml` — RSS-фид последних 20 статей.
- Изображения: `next/image` (или lazy + `srcset`), обязательный `alt`, `loading="lazy"` кроме обложки статьи (`priority`).
- Отложенная публикация: статья со статусом `scheduled` и `publishedAt` в будущем становится доступной автоматически (cron / ISR revalidate).
- Страница статьи отдаётся статически (SSG/ISR) с ревалидацией при публикации через админку (webhook).

## 7. Производительность и доступность

- Lighthouse (mobile): Performance ≥ 90, Accessibility ≥ 95, SEO = 100.
- CLS = 0 — обложки и блок рекомендаций с зарезервированной высотой.

## 8. Трекинг UTM-меток и атрибуция

### 8.1. Что перехватываем

При любом заходе на сайт скрипт читает `window.location.search` и забирает:

**UTM-параметры:** `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`
**Click ID рекламных систем:** `gclid` (Google Ads), `fbclid` (Meta), `ttclid` (TikTok), `msclkid` (Bing)
**Cookie Meta Pixel:** `_fbp`, `_fbc` — читаются из `document.cookie` (нужны для CAPI-дедупликации)

Дополнительно на каждом визите фиксируем:

| Поле | Источник |
|---|---|
| `landing_page` | `location.pathname` первой страницы визита |
| `referrer` | `document.referrer` (пустой = direct) |
| `first_seen_at` | ISO-таймстамп первого визита |
| `last_seen_at` | ISO-таймстамп текущего визита |
| `session_id` | UUID, живёт 30 мин бездействия |
| `client_id` | UUID, живёт 1 год (сквозной идентификатор посетителя) |

### 8.2. Модель атрибуции

Храним **два набора** меток одновременно — это критично для контентного проекта, где путь длинный:

- **First-touch (`attribution_first`)** — записывается один раз при самом первом визите, **больше никогда не перезаписывается**. Отвечает на вопрос «какой канал привёл человека в блог».
- **Last-touch (`attribution_last`)** — перезаписывается при каждом визите, **если в URL есть хотя бы один UTM или click ID**. Если человек пришёл из закладки или direct — старое значение сохраняется (не затираем непустое пустым). Отвечает на вопрос «какой канал дожал конверсию».

> Правило перезаписи last-touch: перезаписываем только при наличии `utm_source` **или** любого click ID. Внутренние переходы по сайту и direct-заходы атрибуцию не сбрасывают.

### 8.3. Хранение

- Основное хранилище — `localStorage`, ключи `attr_first`, `attr_last`, `session`, `client_id`.
- Дублирование в cookie (`SameSite=Lax`, срок 365 дней) — на случай, если форма отправляется с серверного рендера или нужно прочитать метки на бэкенде.
- Объём одного набора — один JSON-объект, не 8 отдельных ключей.

```ts
type Attribution = {
  utm_source?: string;
  utm_medium?: string;
  utm_campaign?: string;
  utm_content?: string;
  utm_term?: string;
  gclid?: string;
  fbclid?: string;
  ttclid?: string;
  msclkid?: string;
  landing_page: string;
  referrer: string;
  timestamp: string;    // ISO
};
```

### 8.4. Куда передаём

**1. В любую форму на сайте (подписка, заявка, контакт).**
В форму добавляются скрытые поля, заполняемые из хранилища при монтировании компонента. В payload на бэкенд уходит:

```json
{
  "name": "...",
  "phone": "...",
  "attribution_first": { "utm_source": "google", "utm_medium": "cpc", "..." : "..." },
  "attribution_last":  { "utm_source": "newsletter", "utm_medium": "email", "..." : "..." },
  "client_id": "uuid",
  "session_id": "uuid",
  "event_id": "uuid",
  "fbp": "fb.1....",
  "fbc": "fb.1....",
  "source_article": { "id": "...", "slug": "..." }
}
```

`source_article` — статья, с которой была отправлена форма (или последняя прочитанная). Это то, что связывает контент с деньгами: видно, какая статья реально приводит заявки.

`event_id` (`crypto.randomUUID()`) генерируется на клиенте, уходит и в Pixel, и на бэкенд — для дедупликации Meta CAPI.

**2. В CRM.**
Метки записываются в кастомные поля карточки лида (в KeyCRM — «Джерело», «Кампанія», «Стаття»). Бэкенд принимает объект целиком и раскладывает по полям — фронт про CRM ничего не знает.

**3. В аналитику.**
События из §3.4 (`article_read_complete`, `recommendation_click`) обогащаются полями `utm_source_first`, `utm_campaign_first`, `client_id`. Так в GA4 можно построить отчёт «какая кампания приводит людей, которые дочитывают статьи до конца».

### 8.5. Сквозные ссылки

- При переходе на внешний домен проекта (например, лендинг приложения с блога) UTM-метки **прокидываются в URL** автоматически — все внешние ссылки на свои домены обрабатываются хелпером `appendAttribution(href)`.
- Внутренние ссылки метки в URL **не тащат** (чтобы не плодить дубли страниц в индексе и не ломать canonical).

### 8.6. Приватность

- UTM-метки и click ID — не персональные данные, собираются без согласия.
- Если на сайте есть cookie-баннер: `client_id` и передача в Meta Pixel/GA4 включаются **только после согласия** на аналитические/маркетинговые cookie. До согласия — метки держатся в `sessionStorage` и не уходят никуда.
- Метки **никогда** не логируются вместе с персональными данными в открытом виде на клиенте.

### 8.7. Критерии приёмки по UTM

1. Заход по `/blog/article?utm_source=facebook&utm_medium=cpc&utm_campaign=test&fbclid=XYZ` → в `localStorage.attr_first` и `attr_last` лежат все 4 параметра.
2. Переход внутри сайта на другую статью → атрибуция не изменилась, `session_id` тот же.
3. Возврат через день по прямой ссылке (без меток) → `attr_first` не изменился, `attr_last` не затёрт пустыми значениями.
4. Возврат по `?utm_source=email` → `attr_first` = facebook, `attr_last` = email.
5. Отправка формы → в payload на бэкенд присутствуют оба набора, `client_id`, `event_id`, `fbp`/`fbc` и `source_article`.
6. В карточке лида в CRM видно первый и последний источник и slug статьи.
7. При отклонении маркетинговых cookie ничего не пишется в `localStorage` и не уходит в Pixel.

## 9. Реализация (два варианта — выбрать под проект)

**Вариант A — Next.js (App Router):**
Роуты `app/blog/page.tsx` и `app/blog/[slug]/page.tsx`, ISR + `revalidateTag` по webhook. Админка — headless CMS: **Sanity** (лучший встроенный редактор и reference-поле для «рекомендованных статей» из коробки) или **Payload CMS** (self-hosted, полный контроль). Тело статьи хранится как Portable Text / Lexical JSON и рендерится собственными компонентами — так вёрстка блоков остаётся под контролем дизайна.

**Вариант B — CMS-портал (Joomla / WordPress):**
Статьи = нативные материалы CMS. Рекомендации — кастомное поле типа «related articles» (ACF Relationship в WP / Custom Fields в Joomla 4+) на 3 элемента + модуль вывода. Триггер «дочитал» и анимация — отдельный JS-файл в теме, без плагина. Автоматический fallback реализуется запросом по taxonomy.

## 10. Критерии приёмки

1. Контент-менеджер публикует статью с обложкой, 3 картинками в теле и видео-эмбедом **без обращения к разработчику**.
2. Черновик открывается по preview-ссылке в приватном окне (без логина) и не индексируется.
3. Статья с датой публикации «завтра 09:00» появляется на сайте автоматически и не видна раньше.
4. В админке к статье вручную привязаны 2 статьи → на публичной странице показываются эти 2 + 1 добранная автоматически, в правильном порядке.
5. Если вручную не привязано ничего → показываются 3 релевантные статьи, текущей среди них нет.
6. Блок рекомендаций появляется с анимацией только после доскролла до конца статьи; при отключённом JS виден статически.
7. В аналитике фиксируются события `article_read_complete` и `recommendation_click` с корректными параметрами.
8. Lighthouse mobile на странице статьи: Performance ≥ 90, CLS = 0.
9. `sitemap.xml` и `rss.xml` содержат новую статью в течение 1 минуты после публикации.
